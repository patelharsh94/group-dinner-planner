# Integration verification and release gates

Reviewed 2026-10-28. Documentation was checked against official sources. No live Telegram token, Muse key, Google OAuth client or Railway deployment is included in this repository. A configured adapter is not evidence of a successful live integration.

- Telegram [Bot API](https://core.telegram.org/bots/api#setwebhook): authenticated webhooks use `X-Telegram-Bot-Api-Secret-Token`; retries require durable update deduplication. Private users must start the bot themselves. `npm run telegram:register` registers the deployed HTTPS endpoint and the **Open planner** Mini App menu without dropping pending updates. Inline/menu Mini Apps use server-validated Telegram `initData`; keyboard-button Mini Apps do not provide the identity proof required here. The existing Render HTTPS hostname is sufficient.
- Meta [Responses API](https://dev.meta.ai/docs/protocols/responses) and [search grounding](https://dev.meta.ai/docs/cookbook/search-grounding): `https://api.meta.ai/v1/responses`, Bearer `MODEL_API_KEY`, configurable `muse-spark-1.3`; structured output uses `text.format`, and web search is a Responses tool. Muse currently accepts only `tool_choice: "auto"`; the application separately requires a completed search call before accepting research. A `/models` discovery rejection does not establish that a key is invalid for `/responses`; troubleshoot the actual endpoint and returned status. Runtime sets `store:false`; provider account retention terms still apply. Live source verification rejects unsupported citations and unreachable/unsafe URLs; these remain unknown instead of being replaced with fixtures. Source interpretation remains subject to model error; participant staff affirmation is required for allergies.
- Google [scopes](https://developers.google.com/workspace/calendar/api/auth) and [free/busy](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query): request only `calendar.freebusy`, query only `primary`. Publish a privacy policy and register the HTTPS redirect URI `/oauth/google/callback`. Confirm the project's consent screen, testing audience and applicable sensitive-scope verification in Google Cloud before public onboarding. Testing restrictions and token lifetime can differ from production; do not claim public access from a developer-account trial.
- Railway: add Postgres, set required environment variables from `.env.example`, deploy Dockerfile, run the configured migration predeploy step, and check `/health` before registering the Telegram webhook. Store the credential encryption key as a stable secret; losing it makes stored tokens unusable. Use one replica for v1's conservative send throughput. Migrations and leases still enforce database consistency.

## Render deployment

Deploy the repository as a Docker web service in the same region as its Render Postgres database. Use one instance and `/health` as the health-check path. Set `DATABASE_URL` to the database's internal connection URL and supply the remaining environment variables from `.env.example`.

The Dockerfile runs migrations at container startup before starting the application. The migration runner is transactional, versioned and protected by a database advisory lock; restarts do not reapply completed migrations. If a migration fails, the container exits without starting the bot. The final `exec` passes shutdown signals directly to Node.

Leave Render's Pre-Deploy Command and Docker Command fields empty to use this startup behavior. A separate paid pre-deploy hook is not required. Once the service's generated HTTPS address is available, set `PUBLIC_URL` to that base address, redeploy, and run `npm run telegram:register` using the same public URL and webhook secret to register both the webhook and planner menu. The app is served at `${PUBLIC_URL}/app/`; no new secret, second service or custom domain is needed.

Render's free web services sleep after 15 minutes without incoming traffic. Background reminders, cleanup and job processing pause while asleep; this setup supports an initial interactive test, but the full always-on trial requires continuously running hosting. This limitation does not remove those features from the agreed scope. See [Render's Docker documentation](https://render.com/docs/docker) and [free-service limitations](https://render.com/docs/free).

## Optional Yelp Places discovery

Reviewed 2026-11-03 against Yelp's [Places introduction](https://docs.developer.yelp.com/docs/places-intro), [business search](https://docs.developer.yelp.com/reference/v3_business_search), [business details](https://docs.developer.yelp.com/reference/v3_business_info), and [FAQ](https://docs.developer.yelp.com/docs/places-faq). `YELP_API_KEY` authenticates with Bearer authentication. `YELP_CLIENT_ID` is optional account metadata and is not used in Places requests.

`YELP_USAGE_MODE` defaults to `disabled`. `evaluation` reserves trial credentials for separate evaluation checks; it does not enable Yelp for live dinner planning. Set `production` only after verifying that the account's plan permits the deployed use. The official FAQ says trial API calls are strictly for evaluation and not commercial deployment; adding credentials to Render does not establish production eligibility. Keep the mode disabled while that plan status is unknown. Existing independent web research remains available.

The adapter only calls `https://api.yelp.com/v3/businesses/search` and `/businesses/{id}` with redirects disabled and a 15-second maximum request deadline. It makes no retries and limits search to five businesses. Search sends aggregate public city, area and cuisine text only; callers must exclude participant identities, calendar entries, travel origins and private health details. Yelp discovery does not establish reservation inventory, dietary safety or staff affirmation. Price levels such as `$$` are relative tiers, not per-person prices. Regular hours are local recurring opening periods, not a guarantee that a restaurant is open for a requested date.

Normalized business content is ephemeral: business ID, name, Yelp profile URL, address, city, phone, relative price level, categories, regular hours, retrieval and expiry timestamps. The adapter deliberately excludes ratings, reviews and photos. Its memory cache defaults to 15 minutes, is bounded to 100 entries, expires strictly, and is purged at least every minute; configurable TTL is capped at 23 hours. Expired results are never served on upstream failures. Yelp's FAQ allows content caching for at most 24 hours and business IDs indefinitely. Do not copy Yelp content into dinner state, proposals, outbox messages, histories, model logs or diagnostics. Only business IDs may be retained as matching identifiers. Downstream research must independently corroborate restaurant facts using non-Yelp sources before retaining them.

Where Yelp content is displayed, use the current [Yelp display requirements](https://www.yelp.com/developers/display_requirements), attribute Yelp and link directly to the original returned Yelp profile. The current integration uses candidates transiently for independent research; it does not display Yelp ratings, reviews or photos. Test coverage uses fake transports and synthetic public business fixtures; no successful live request or account entitlement is implied. Safe errors distinguish authorization failure (401/403), quota limits (429), invalid data, network failure and other upstream failures without including provider response bodies or credentials.
